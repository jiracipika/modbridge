## THE DOCUMENTED 5.11 WALL — diagnosis corrected, then fallen

The 5.11 close framed the wall as "moonlight's lazy DeferredRegister creation vs
21.1 registry event order". GROUND TRUTH (this slice): the mob_effect
DeferredRegister IS created during construction (ModRegistry.<clinit> ->
RegHelper.registerEffect -> RegHelperImpl.register -> computeIfAbsent ->
DeferredRegister.create + register(bus) - read off the raw bytecode). The REAL
failure was INSIDE the mob_effect RegisterEvent dispatch itself:

  1. DeferredRegister.addEntries ran the effect suppliers; entry 1
     (supplementaries:overencumbered) constructed OverencumberedEffect, whose ctor
     calls the 21.1-removed MobEffect.addAttributeModifier(Attribute, String uuid,
     double, Operation) -> NSFE ("Attributes does not have member field 'Attribute
     MOVEMENT_SPEED'" desc drift + the removed ctor) -> the addEntries loop ABORTED
     -> entry 2 (supplementaries:flammable) NEVER REGISTERED.
  2. The 5.11-documented "registry value not present: mob_effect/
     supplementaries:flammable" was the downstream symptom: supp's fluid-item
     supplier (ModFluids.lambda$static$2) queried the flammable wrapper during the
     ITEM event and the EntryWrapperCompat lookup correctly found nothing.

THE FIX (no registry-lane change at all - moonlight's constructs untouched):
- rules: 4x Attributes field desc retargets (Attribute -> Holder; MOVEMENT_SPEED
  was the boot wall, FOLLOW_RANGE/ATTACK_DAMAGE/ATTACK_SPEED census-complete),
  "*"-owner memberretarget for MobEffect.addAttributeModifier -> the new
  MobEffectCompat shim (uuid String -> "modbridge/<lowercase uuid>"
  ResourceLocation key; the 21.1 ctor takes (Holder, ResourceLocation, double,
  Operation)), + the "*" owner fallback for FIELD retargets (javac emits the
  SUBCLASS as owner for inherited statics - OverencumberedEffect called the
  MobEffect member it inherits).
